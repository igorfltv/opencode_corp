# Company OpenCode: корпоративный плагин и сервер-эмулятор

Рабочий прототип для **OpenCode 2.0.24** и **Bun 1.3.14**. Он регистрирует
настоящие slash-команды через API плагина. Для входа, конфига, forms и skills
запрос к языковой модели не нужен.

## Подключение из GitHub

В `~/.config/opencode/opencode.jsonc` укажите:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "plugins": ["github:igorfltv/opencode_corp#main"]
}
```

OpenCode v2 устанавливает Git-плагин из пакета в корне репозитория. В корне
лежат собранные `server.js` и `tui.js`; сборка на компьютере пользователя не нужна.
Команда разработки называется `bun run bundle`: npm запускает дополнительную
подготовку Git-зависимости, если в пакете есть lifecycle-скрипт `build`.
Существующие настройки в `opencode.jsonc` можно сохранить: достаточно заменить
локальный путь в массиве `plugins` на GitHub-запись. Для обновления ветки
используйте `opencode plugin update github:igorfltv/opencode_corp#main` либо
перезапустите OpenCode и проверьте статус плагина.

Плагин по умолчанию использует обычный профиль OpenCode, файл подключения
локального сервиса и эмулятор на `http://127.0.0.1:4310`. Для проверки всего
сценария запустите сервер из исходников: `bun run server`, затем в OpenCode
выполните `/login`. Настройки можно переопределить через поля `options` записи
плагина или переменные `CORP_PROFILE_DIR`, `CORP_SERVER_URL`,
`CORP_OPENCODE_CONNECTION_FILE`.

## Быстрый запуск

```sh
git clone https://github.com/igorfltv/opencode_corp.git
cd opencode_corp
bun install --frozen-lockfile
bun run bundle
bun run demo
```

Откроются отдельный OpenCode в браузере и панель эмулятора. В OpenCode откройте
сессию «Корпоративный плагин · демо» и начните с `/login`.
Если одноразовая ссылка входа в сам интерфейс OpenCode истекла: `bun run demo:open`.

Демо использует свою папку `.demo`: config, credentials, sessions, cache и проект.
Рабочие `~/.config/opencode/opencode.jsonc` и авторизация пользователя не меняются.
Сам бинарник берётся из установленного приложения:
`/Applications/OpenCode.app/Contents/Resources/opencode-cli`.
Другой путь можно задать через `OPENCODE_BIN`.

Панель сервера: <http://127.0.0.1:4310/admin>. Если порт занят, запустите
`PORT=0 bun run demo` и используйте адрес из терминала. Остановка — `Ctrl+C`.
Эмулятор хранит пользователей и токены в памяти; после его перезапуска нужен
новый `/login`. Skills и демоконфиг сохраняются в `.demo`.

## Проверка в своём OpenCode

Если приложение OpenCode уже запущено, из этой папки выполните `bun run install:local`.
Команда собирает плагин и добавляет его в `~/.config/opencode/opencode.jsonc`.
Она сохраняет исходный файл в `opencode.jsonc.before-corporate-plugin.bak`,
не меняет остальные плагины, провайдеры и текущую авторизацию. Настройки плагина
указывают на этот каталог, локальный эмулятор и служебный файл подключения
работающего OpenCode. Файл `~/.local/state/opencode/service.json` содержит пароль
локального API; плагин читает его при каждом обращении, поэтому повторно открывать
формы можно и после смены порта сервера OpenCode.

Пока работает `bun run demo`, эмулятор доступен на <http://127.0.0.1:4310/admin>.
Если демо остановлено, запустите отдельно `bun run server` в этой папке. После
перезапуска эмулятора потребуется новый `/login`, поскольку его тестовые токены
хранятся в памяти.

В своём приложении начните с `/corp_status`, затем `/login`. Выберите тестовую
учётную запись в браузере. Вызовите `/skills_load` и отметьте нужные skills.
В панели эмулятора опубликуйте новую версию и выполните `/refresh_config`;
переключите нагрузку на красную и вызовите `/inference_status`. Через `/logout`
можно удалить тестовый токен и корпоративного провайдера. Остальные модели останутся.

Эта установка предназначена для проверки прототипа на машине разработчика.
Тестовый backend и фиктивная учётная запись не подходят для рабочих данных.

## Команды

| Команда | Что происходит |
|---|---|
| `/login` | Открывает браузер с тестовым SSO. После выбора учётной записи получает токен и конфиг, обновляет JSONC и сообщает о результате во встроенной форме OpenCode. |
| `/refresh_config` | Проверяет авторизацию, получает актуальный конфиг с ETag и применяет новую версию. |
| `/skills_load` | Получает доступный этой учётной записи каталог и показывает встроенную multiselect-форму OpenCode. Загружает выбранные skills. |
| `/inference_status` | Обновляет и показывает светофор нагрузки. |
| `/corp_status` | Показывает пользователя, версию конфига, время проверки, ошибки синхронизации и нагрузку. |
| `/logout` | Удаляет локальный токен, отключает корпоративного провайдера и пытается отозвать токен на сервере. Скачанные skills остаются. |

Авторизация в демо — выбор одной из двух фиктивных учётных записей.
Пароля нет: Engineering получает три skills, Analytics — один.
Это заменяемая часть для настоящего корпоративного OIDC/SSO.

## Сценарий демонстрации

1. Введите `/login`. Выберите Engineering в открывшейся странице, нажмите «Войти».
2. Выполните `/corp_status`: появятся пользователь и версия конфига.
3. В панели эмулятора измените название модели и опубликуйте новую версию.
4. Выполните `/refresh_config`: `providers.corporate` обновится в демоконфиге.
5. Введите `/skills_load`, отметьте несколько пунктов и отправьте форму.
6. В панели нажмите «Перегрузка». Не позднее следующего 30-секундного опроса
   придёт уведомление с 🔴. `/inference_status` позволяет проверить сразу.
7. «Включить сбой API» даёт ⚪ и сохраняет последний конфиг. «Восстановить API»
   возвращает нормальную работу. «Завершить сессии» проверяет повторный `/login`.
8. Выполните `/logout`.

В панели есть журнал действий без токенов и запросов к модели. Кнопка публикации
увеличивает ревизию. Изменение нагрузки не требует новой версии конфига.
Макет inference API возвращает фиксированное сообщение, а не результат LLM.

## Автоматическая работа и уведомления

- Конфиг проверяется **раз в час**, а также при запуске уже авторизованного профиля.
- Нагрузка проверяется каждые **30 секунд**. 🟢 — норма, 🟡 — повышенная нагрузка,
  🔴 — перегрузка, ⚪ — нет актуальных данных или нужна авторизация.
- Уведомления нагрузки приходят при смене цвета; одинаковые состояния не спамят.
- Один runtime на профиль в одном процессе OpenCode обслуживает все проекты;
  при выгрузке последнего экземпляра таймеры и незавершённый вход отменяются.
- В TUI подключён отдельный UI entrypoint с toast-уведомлениями. На macOS используется
  системное уведомление, на Linux — `notify-send`, если установлен. Показ системных
  уведомлений зависит от настроек ОС. Windows не имеет OS-адаптера в этом прототипе.
- В браузере/desktop статус всегда доступен через `/inference_status` и `/corp_status`.
  Постоянный виджет в панели desktop OpenCode не добавлен: TUI slots не являются API
  расширения desktop. Сам светофор постоянно виден в панели эмулятора.

Чтобы быстро показать фоновое обновление, запустите:

```sh
CORP_REFRESH_INTERVAL_MS=10000 CORP_LOAD_INTERVAL_MS=2000 bun run demo
```

Это только ускорение демо; значения по умолчанию — 3 600 000 и 30 000 миллисекунд.

## Конфиг и credentials

Плагин управляет только зарезервированным разделом `providers.corporate`.
Другие провайдеры, default model, плагины, permissions и пользовательские комментарии
сохраняются. Новые `plugins`, `mcp`, shell-команды и произвольные адреса из серверного
конфига не принимаются. В демо inference URL обязан совпадать с адресом эмулятора + `/v1`.

В `opencode.jsonc` записывается ссылка `{file:.../corporate-state/access-token}`.
Сам токен хранится отдельно, с правами `0600`, и не попадает в формы, RPC status,
уведомления, журнал эмулятора или ответы модели. Файлы состояния находятся в профиле:

```text
config/opencode/
  opencode.jsonc
  opencode.jsonc.before-corporate.bak
  opencode-connection.json
  corporate-state/
    credential.json
    access-token
    sync.json
  skills/corp-*/SKILL.md
```

JSONC изменяется через `jsonc-parser` и атомарный rename; перед первым изменением
создаётся backup. Некорректный JSONC не перезаписывается. Более старая серверная версия
или другое содержимое под той же ревизией отклоняются. `304 Not Modified` не переписывает
конфиг. OpenCode перечитывает файл своим watcher, без перезапуска активной сессии.

Вход использует одноразовый код, PKCE S256, случайный `state`, callback на
`127.0.0.1` со случайным портом и ограниченное время жизни. Access token не передаётся
в URL. Это демонстрационный auth-протокол, а не готовый OIDC-клиент.

`/logout` при недоступном сервере всё равно удаляет локальный токен; серверная копия
в таком случае остаётся действительной до истечения срока. При синтаксически сломанном
JSONC токен удаляется/отзывается, но исправление самого файла остаётся пользователю.

## Skills

Каталог фильтруется сервером по роли. Плагин принимает только `corp-*` IDs,
проверяет SHA-256 скачанного `SKILL.md` и не следует символическим ссылкам при записи.
Произвольно изменённый локальный skill не перезаписывается.
Файлы всех выбранных skills проверяются перед записью; каждый файл заменяется атомарно.
Это не транзакция всей группы: при сбое диска часть группы может уже установиться.
Неотмеченные skills не удаляются. Обновление skill требует повторного `/skills_load`.

SHA-256 проверяет соответствие содержимого каталогу; цифровая подпись издателя
в этой версии не реализована. Каталог и файлы доверяются корпоративному HTTPS-серверу.

В OpenCode 2.0.24 форма может показывать пункт «Введите свой ответ» даже при
`custom: false`. Неизвестные IDs сервер и плагин отклоняют; для установки выбирайте
пункты каталога. Для отображения форм в браузере используется `metadata.kind: question`.

## Поставка вместе с OpenCode

```sh
bun run pack
```

Получится `artifacts/company-opencode-0.1.0.tar.gz`: серверный и TUI entrypoint,
manifest и инструкция. Runtime-зависимости включены в bundle. Эмулятор в этот архив
не входит; его исходники находятся в `server/`.

Для корпоративной сборки:

1. Зафиксировать совместимую версию OpenCode и положить распакованный плагин
   в поставку. В `plugins` демо используется абсолютный путь к папке плагина.
2. Launcher запускает OpenCode с корпоративным профилем и задаёт переменные ниже.
3. Launcher передаёт endpoint и пароль **своего** OpenCode-процесса через файл
   соединения `0600`. Плагин использует его для встроенных форм через локальный API.
   В прототипе это делает `scripts/harness.mjs`; текущий пользовательский сервер не используется.
4. В настоящем контуре заменить эмулятор на OIDC backend, утвердить контракт конфига
   и механизм хранения credentials, затем прогнать сквозные тесты на версии поставки.

| Переменная | Назначение |
|---|---|
| `CORP_PROFILE_DIR` | Папка корпоративного профиля, содержащая `opencode.jsonc`. |
| `CORP_SERVER_URL` | Адрес корпоративного backend. HTTPS обязателен, кроме loopback-эмулятора. |
| `CORP_OPENCODE_CONNECTION_FILE` | JSON `{ "url": "http://127.0.0.1:port", "password": "..." }` для форм своего процесса. |
| `CORP_REFRESH_INTERVAL_MS` | Интервал config sync; по умолчанию 1 час. |
| `CORP_LOAD_INTERVAL_MS` | Интервал нагрузки; по умолчанию 30 секунд. |
| `CORP_NO_BROWSER`, `CORP_NO_NOTIFICATIONS` | `1` отключает соответствующий OS-адаптер в автоматических тестах. |
| `OPENCODE_BIN` | Путь к совместимому CLI для launcher. |

Внешний `/login` открывается на машине, где работает сервер OpenCode. Для удалённого
агента нужны device authorization flow либо браузерный callback на клиенте.
Этот прототип предназначен для локальной поставки OpenCode.

## Контракт сервера

| Endpoint | Авторизация / результат |
|---|---|
| `POST /oauth/requests` | PKCE challenge, state и loopback redirect URI → URL входа. |
| `GET /oauth/authorize` | Форма тестового входа. |
| `POST /oauth/approve` | Тестовая учётная запись + CSRF → одноразовый code в callback. |
| `POST /oauth/token` | Code + verifier → accessToken, expiresAt, user, configuration. |
| `POST /oauth/revoke` | Bearer; отзыв текущего токена. |
| `GET /api/config` | Bearer; `{revision, config}`, ETag / 304. |
| `GET /api/load` | Bearer; level, queue, observedAt, message. |
| `GET /api/skills` | Bearer; доступные IDs, описание, версия и SHA-256. |
| `GET /api/skills/:id` | Bearer; содержимое разрешённого `SKILL.md`. |
| `GET /admin` | Локальная панель, не предназначена для публикации в сети. |
| `GET/POST /admin/state` | Токен панели + проверка Origin для изменения демосостояния. |

## Проверки

```sh
bun test tests
bun run bundle
bun run test:integration
```

12 тестов проверяют PKCE/state/replay, роли, отзыв токена, JSONC, пути skills,
контрольные суммы, локальные правки, нагрузку и гонку смены учётной записи.
Интеграционная проверка запускает **настоящий установленный OpenCode**, выполняет
команды и отвечает на встроенные формы через API. Проверяются вход, live config reload,
ручная и автоматическая синхронизация, skill discovery, нагрузка, сбой API, истечение
токена и logout. Для автоматической синхронизации используется ускоренный интервал;
ожидание реального часа не требуется. Модель и рабочие пользовательские сессии не используются.

Нативный показ OS-уведомлений и TUI toast зависит от хоста; полный сценарий TUI
не автоматизирован. Источник контракта: [OpenCode 2.0.24 Plugin API](https://github.com/anomalyco/opencode/blob/v2.0.24/packages/plugin/src/promise/plugin.ts),
[Commands](https://github.com/anomalyco/opencode/blob/v2.0.24/packages/plugin/src/promise/command.ts),
[Forms](https://github.com/anomalyco/opencode/blob/v2.0.24/packages/schema/src/form.ts).

## Перед реальной корпоративной эксплуатацией

Нужно заменить тестовую авторизацию на корпоративный OIDC, добавить хранение токена
в OS keychain, refresh/rotation, подпись конфигов и skills, rollout/rollback,
серверный RBAC и промышленное хранилище. Managed JSONC — настройка клиента, а не
граница безопасности: обязательные политики и ограничения доступа должны исполняться
на корпоративном gateway. Панель эмулятора и его фиктивный inference API не являются
production-сервисами. Идеи следующего этапа — в [ROADMAP.md](ROADMAP.md).
